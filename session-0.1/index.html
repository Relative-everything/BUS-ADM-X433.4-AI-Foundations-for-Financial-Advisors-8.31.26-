04 · Flagship16 min

The context window inspector

Twelve controls, twelve context blocks, three probe prompts, and 38,016 legal configurations. Flip a control and watch which block fills, what the output gains, and what the signals do.

Why this is not a lookup table The obvious way to build this is a grid of pre-written outputs. Here is what that costs, computed rather than asserted, by scripts/state_space.py, which ships with this lesson so the figure is reproducible:
  • Legal configurations, dependencies enforced: 38,016
  • Naive independent grid, no dependency pruning: 138,240
  • Illegal states the naive grid would expose: 100,224, which is 72.5% of it
  • Coverage of a hand-written 50-cell lookup table: 0.132%, leaving 37,966 dead ends
So this is a compositional engine instead: three captured base outputs plus 23 authored delta fragments, 26 strings covering all 38,016 states, roughly 1,462 states per string. The point is not the saving. It is that a lookup table teaches “this combination produces that output”, which is memorisation, and composition teaches “each control injects a specific thing, and the output is the sum”, which is the actual model and transfers to controls that ship after this class.

The four rungs

RungWhat it puts in the contextWhat you see in the output
0 · NothingOnly the weights, plus whatever the other four layers already carried.No citations, no as-of date, and no way to tell from the surface of the text whether the facts are current.
1 · Past-chat searchRetrieved slices of your own earlier conversations. Paid plans only. Scope is every chat outside projects; inside a project, that project only. HTool calls in the conversation. The load-bearing consequence Rungs 1, 2 and 3 all show up in the output as tool calls. Rung 0 shows up as nothing at all. That asymmetry is the entire basis of section 9: you can see that retrieval happened, but you cannot see that it did not, except by its absence, and absence is exactly what a fluent answer is good at hiding.

One more thing about rung 1, and it matters for an RIA specifically: on Enterprise plans with customer-managed keys, past-chat search does not work at all, because the content is encrypted and cannot be indexed. Which controls does this firm turn off?

The Cole file is the reason this is not abstract. A closely held business, an unsigned buy-sell, a son who has not been told, and a discount nobody has re-verified. Which of tonight’s controls does your firm leave on when that file is open?

Requires instructor verification before it is taught as settled This section is a contested judgment, not a settled question, and nothing in it has been verified against primary authority by this build. Every regulatory characterisation below is posed as a question. Verify each against primary authority before answering any of them in class:
  • Does a chat with a general-purpose AI tool constitute a communication or a record that must be retained, and under which rule?
  • If it is a record, does an incognito chat that appears in the organisation’s data export satisfy retention, or create an unindexed one?
  • What supervisory obligation attaches to a tool an employee configures individually, where the firm has no administrative control over the setting?
  • Does a memory entry generated from a client conversation become a record, separately from the conversation it came from?
  • Is a policy that the firm cannot technically enforce a supervisory system, or a statement of intent?
  • What does the answer to any of the above depend on: the plan tier, the entity’s registration, or the content of the chat?
